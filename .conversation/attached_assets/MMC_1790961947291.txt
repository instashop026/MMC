Build Specification: Mobile-First Model Feed / Content Catalog 1. ROLE 

You are the primary full-stack engineer for this project.

Build the application completely inside Replit as a production-ready, mobile-first web application that can later be deployed to Netlify.

Do NOT use Replit-specific backend services or infrastructure.

The final application must be deployable to:

Netlify Static Hosting Netlify Functions Supabase ZeroStorage 

The application should remain simple, maintainable, modular, and understandable.

Do NOT introduce React, Next.js, Express, or another heavy framework unless there is a concrete technical requirement that cannot be solved with the requested stack.

2. REQUIRED TECHNOLOGY STACK 

Use:

TypeScript Vite Vanilla TypeScript / DOM APIs HTML CSS Supabase JS client Netlify Functions Supabase PostgreSQL Supabase Auth Supabase Row Level Security ZeroStorage API 

Do NOT use:

React Next.js Express Replit Database Replit Auth Firebase Netlify Blobs as the primary database a custom VPS backend 

Keep dependencies minimal.

3. DEPLOYMENT ARCHITECTURE 

The final architecture must be:

Browser ↓ Netlify CDN / Static Site ↓ Vite-built frontend ↓ Supabase ├── Authentication ├── PostgreSQL └── RLS

Admin-only/server-side operations:

Browser ↓ Netlify Function ↓ ZeroStorage API

Never expose the ZeroStorage API key to the browser.

Never expose Supabase Service Role key to the browser.

9. CONTENT SOURCES 

Create a backend source abstraction because current content comes from different sources.

Sources currently are:

ctele eb wt 

Important:

CTele and EB contain image galleries.

WT contains videos only.

There are NO videos in CTele or EB.

WT does NOT contain image galleries.

Do not infer video content from CTele/EB album titles.

For example, a title such as:

"76 photos and 1 video"

is simply metadata from the scraped source and DOES NOT mean that a video should be imported.

content_sources 

Fields:

id UUID source external_id model_id album_title source_url raw_metadata JSONB created_at 

Source should support:

ctele eb wt 

Add a unique constraint where appropriate on:

source + external_id

This table is metadata only.

It is NOT a public gallery entity.

10. POSTS 

Create one unified posts table.

Every media file is an independent post.

Fields:

id UUID model_id content_source_id nullable type zerostorage_file_id filename nullable caption nullable source source_path nullable published created_at updated_at 

type must be:

image video 

zerostorage_file_id is extremely important.

Use it as the canonical ZeroStorage identity.

Add a unique constraint to prevent importing the same ZeroStorage file twice.

13. RLS SECURITY 

Enable Row Level Security on all user-accessible tables.

Public users should be able to read only published public content.

Users should only be able to modify their own:

profile where appropriate follows likes mmcs comments 

Users must not be able to:

create models delete models create arbitrary posts change another user's profile modify another user's likes modify another user's MMC modify another user's comments 

Admin operations must be restricted to users whose profile role is admin.

Do not rely only on hiding UI elements.

Backend/database security must enforce permissions.

14. ZERO STORAGE 

ZeroStorage is the media provider.

Current root structure:

0RMCOIN/

Ctele/ model folders/ gallery folders/ image files EB/ model folders/ gallery folders/ image files WT/ model folders/ video files 

Important:

CTele = images only EB = images only WT = videos only 

Do not create a separate public Gallery system.

Folders are primarily an organizational/import concept.

Every actual media file becomes an independent Post.

15. ZERO STORAGE API 

ZeroStorage API documentation:

https://test.zerostorage.net/docs/api/upload

The API requires an API key.

The API key must NEVER be sent to the browser.

Implement ZeroStorage access through Netlify Functions.

Create a service abstraction such as:

netlify/functions/ zerostorage-folders.mts zerostorage-files.mts zerostorage-file.mts

And/or a reusable server-side ZeroStorage service module.

16. ZERO STORAGE URL HANDLING 

Do NOT trust old URLs stored in CSV/source data.

The ZeroStorage File ID is the canonical identity.

Current image embed format:

https://test.zerostorage.net/embed/image/{FILE_ID}

Current video embed format:

https://test.zerostorage.net/embed/{FILE_ID}

Current download format:

https://test.zerostorage.net/api/files/download/{FILE_ID}?track=true

Build these URLs programmatically.

Do not hard-code old upload.zerostorage.net URLs.

Do not store the old URLs as the canonical media identity.

Store:

zerostorage_file_id

Then generate current URLs from that ID.

Create helper functions:

buildImageEmbedUrl(fileId) buildVideoEmbedUrl(fileId) buildDownloadUrl(fileId)

Keep all ZeroStorage URL construction in one place.

20. DUPLICATE DETECTION

zerostorage_file_id

If that ID already exists:

Do not create another post.

Show a useful admin message:

"Already imported"

and identify the existing post.

This must be enforced at the database level with a unique constraint, not only frontend logic.
